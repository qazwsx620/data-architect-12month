## 一、架构题 10 题口述稿

### Q1 实时 vs 离线数仓区别？
| 维度 | 实时 | 离线 |
|------|------|------|
| 时效 | 秒/分钟级 | T+1 级 |
| 计算 | 流式 Flink | 批量 SQL |
| 存储 | Kafka topic / Flink 状态 | Hive 表 / HDFS |
| 口径 | 窗口近似 | 精确 |

### Q2 四层职责 + 存储计算？
ODS 原始流 / DWD 清洗过滤口径统一 / DWS 轻度汇总 / ADS 报表大屏。
存储：Kafka topic；计算：Flink SQL。
分层价值：ODS 保留可回溯、DWD 口径集中、DWS 复用、ADS 服务应用。

### Q3 Lambda vs Kappa？
- Lambda：离线 + 实时双链路，两套代码两套口径，维护贵、可能对不上（所以要对账）
- Kappa：纯实时单链路，靠 Kafka 重放重算，重算贵、受留存期限制

### Q4 双链对账？
定时比对同一指标，差异超阈值告警排查。
前提：口径统一（status=2）。
常态差异：窗口近似、数据迟到、数据丢失、过滤口径错误。

### Q5 维表关联？
- 缓存：查一次缓存进本地状态，减少查库
- 异步 IO：异步并发查维表，不阻塞主线程，提吞吐
- 广播流：维表存广播流，并行子任务实时更新缓存
查不到：默认兜底值 + 侧输出流单独收集，维表更新后回补关联。

### Q6 端到端 Exactly-Once 三段式？
source offset 随 checkpoint → 中间算子状态与 offset 同一次快照原子写入 → sink 两阶段提交（预提交→快照完成→提交；失败回滚）。

### Q7 背压排查与处理？
定位：Web UI → Job → SubTasks，第一条 HIGH 边的下游算子是瓶颈。
处理：外部写慢攒批/异步、倾斜加盐两阶段聚合、瓶颈算子单独提并行度、GC 调堆、状态大换 RocksDB。

### Q8 实时报表延迟？
两直接环节：窗口粒度、落库写入策略。
只写聚合不写明细：写入压力 + 表用途（大屏要汇总）+ 行数少点查快省存储。

### Q9 Watermark 与乱序？
Watermark=水位线（事件时间 ≤ 它的数据都已到达）；早到数据被窗口收下，watermark 越过窗口结束时间触发计算；触发=watermark ≥ 窗口结束；清窗=watermark ≥ 窗口结束 + allowedLateness。

### Q10 项目四段式（背景/架构/关键设计/成果）
背景：GMV 实时大屏需求。
架构：Kafka → Flink SQL 四层（ODS/DWD/DWS/ADS）。
关键设计：① 口径 status=2 实时离线统一 ② 容错 checkpoint+offset ③ 可靠性窗口迟到 + 双链对账。
成果：秒级 GMV 输出，离线实时对账一致。
加分句：本地 demo 跑通，生产差距在事件时间 + RocksDB 大状态 + YARN 资源管理，已知差距。

## 二、概念题 5 题

C1. Checkpoint 自动故障恢复 / Savepoint 手动运维。
C2. 小状态 HashMap / 大状态 RocksDB。
C3. 滑动窗口可重叠 → 一条数据可属两个窗口。
C4. SQL：简单统计/报表/多表 join；DataStream：复杂状态/自定义 watermark/触发器/特殊分流。
C5. 3 分区 topic 同组最多 3 个消费者（每分区 1 个）。

## 三、场景题 2 题

### S1 延迟上涨 + lag 持续上涨排查链（6 步）
① Web UI 看背压（HIGH 边下游=瓶颈）
② consumer-groups.sh --describe 看 lag 分布（单分区还是全部分区）
③ 区分生产过快 vs 消费过慢（消费者 Records consumed rate 是否掉）
④ 下游 Sink 写慢 → 攒批/批量/异步 IO
⑤ 数据倾斜（热点 key）→ 加盐+两阶段聚合
⑥ 资源：CPU 打满、GC/堆 OOM、checkpoint 频繁失败

### S2 热点 key 倾斜处理
① key 加盐 + 两阶段聚合（先加盐局部预聚合，再去盐全局聚合，摊平热点）
② 热点 key 单独识别走单独通道
③ 倾斜 join：小表广播（BroadcastState）
④ 坑：单纯提并行度对倾斜无效（热点 key 仍哈希到同一 subtask）

## 易混淆坑
- 消费组上限 = 分区数（3 分区 3 消费者），不是 1
- 倾斜时提并行度没用，要加盐两阶段聚合
- 背压瓶颈是 HIGH 边的下游
- Lambda 双链路代价=维护贵+口径可能不一致；Kappa 代价=重算贵
- 端到端 Exactly-Once 要三段式，光 source 或光 sink 都不够
