# Day92 总结笔记：指标平台

> 日期：2026-11-06 ｜ 模块七：数据平台工程 ｜ 状态：✅ 理论 + 指标字典实操完成

## 一、指标体系三层结构

```
原子指标（业务过程 + 度量，不可再拆，全仓口径唯一）
  → 派生指标（原子 + 时间/维度/修饰词）
    → 复合指标（多个指标运算：比率/差值）
```

| 层级 | 定义 | 例子 | 易混淆点 |
|---|---|---|---|
| 原子 | 业务过程+度量，不可拆 | GMV=`SUM(pay_amount) WHERE status=2`、订单量=`COUNT(DISTINCT order_id)` | 口径必须全仓唯一 |
| 派生 | 原子 + 限定（时间/维度/修饰） | 近7天GMV（滚动窗口）、新客GMV、品类GMV | **近7天GMV 是派生，不是复合** |
| 复合 | 指标间运算 | 客单价=GMV÷订单量、复购率、支付转化率 | **客单价是复合，不是原子** |

## 二、口径管理

**口径不统一的后果**：同名不同义（含不含退款/运费、按 create_time 还是 pay_time）、报表打架、离线实时对账不平、决策失误。

**口径管理三件事**：
1. **指标字典（唯一权威源）**：指标名、业务含义、计算公式、时间口径、排除规则、维度、数据源、负责人、版本
2. **评审流程 + 版本化**：新增/变更评审，v1.0→v1.1 记录变更原因与生效时间
3. **下发与校验**：BI/API/报表全引用字典；定期对账（报表 vs 明细、离线 vs 实时）

**口径变更标准流程**：
- 变更前：**血缘影响分析**（Day90 的自动血缘查下游）
- 变更中：**双写/灰度**，新旧口径并行对比
- 变更后：更新字典版本 + 通知下游 + 对账验证

## 三、指标平台四层

```
定义层（字典/公式/口径/版本）
  → 计算层（离线 Spark/Hive T+1；实时 Flink）
    → 存储层（ADS 指标表 / Redis / ClickHouse）
      → 服务层（查询 API / BI / 权限 / 缓存）
```

核心设计：**定义与计算分离**（改口径只改定义，不改成百上千条 SQL）；**离线实时读同一份定义**（防对账不平）。

平台价值：复用、一致、可管理（版本+影响分析）、可发现（字典可搜）。

**指标平台 ≠ BI**：平台管定义/计算/口径，BI 只管展示。

## 四、实操：订单数仓指标字典（scripts/day92/指标字典.md）

6 个指标设计完成，批改修正 3 处：
1. 订单量：`count(pay_order)` → `COUNT(DISTINCT order_id)`（字段不存在 + 一单多明细需去重）
2. 客单价数据源：不是扫 `dwd_order_detail`，而是 **GMV/订单量指标结果相除**
3. 近7天GMV：`timestamp-pay_time` 写法不通 → `pay_time >= NOW()-INTERVAL 7 DAY AND < NOW()`（滚动窗口）
4. 新客GMV："and 新注册"不可执行 → 定义 `is_new_user=1`（首次购买口径，依赖 dim_user）

## 五、面试答案

**指标口径怎么统一**：指标字典（唯一权威定义）+ 评审流程 + 版本化 + 对账校验。
**指标平台怎么设计**：定义→计算→存储→服务四层，定义与计算分离，离线实时同一定义，口径版本化 + 血缘影响分析。

## 七、易混淆坑

- 客单价 = 复合（GMV/订单量），不是原子
- 近7天GMV = 派生（加时间限定），不是复合
- 原子口径错一个，派生/复合全错
- 指标平台不是再做一套 BI
- "口径统一"= 唯一权威源 + 流程 + 版本 + 校验，不是写个文档
