## 一、Kafka 10 题口述稿

### Q1 Kafka 为什么快？
顺序写磁盘（追加、避免随机寻道）+ 页缓存（读写走内存）+ 零拷贝 sendfile（内核态直达网卡，不进用户态）+ 分区并行 + 批量攒批压缩。

### Q2 Topic/Partition/Offset/副本关系？
- topic：消息逻辑分类
- partition：topic 内的并行单元
- offset：分区内消息递增序号（非 topic 全局）
- 副本：分区冗余备份；leader 读写，follower 同步备份；leader 挂 ISR 内 follower 上位

### Q3 消费组机制？
同一分区同组内一个时刻只能被一个消费者消费；**同组最大有效消费者数 = 分区数**，多出的闲置；不同组互不影响，各自拿全量（广播原理）。

### Q4 三种投递语义？
- at-most-once：最多一次，可能丢不重复；先提交 offset 再执行业务
- at-least-once：最少一次，不丢可能重复；先执行业务成功再提交 offset
- exactly-once：不丢不重；Kafka 自身靠幂等 producer（PID+序号）+ 事务 API；Flink 端到端三段式见 Q6

### Q5 offset 存哪？自动/手动提交？Flink 怎么管？
- 存储：Kafka 内部主题 `__consumer_offsets`（新版；老版本存 ZK）
- 自动提交 auto.commit.enable=true：后台按周期提交，不管是否处理完 → 可能重复
- 手动提交 commitSync/commitAsync：业务成功后再提交，可控
- Flink KafkaSource：offset 纳入 Flink 状态随 Checkpoint 快照，恢复时从快照 offset 续读；端到端还要 Sink 事务配合

### Q6 Rebalance 触发与影响？
触发：新消费者加入/宕机退出、心跳超时、超 max.poll.interval.ms、扩分区、订阅变化。
影响：重平衡期间整组短暂停止消费、可能重复消费、吞吐下降。
预防：调大超时参数、消费逻辑别做重操作、静态成员 group.instance.id。

### Q7 有序性？
分区内单消费者顺序拉取、offset 递增 → 严格有序；跨分区并行 → 全局无序。
按键有序（同 key 同分区）是最常用折中；全局强有序只能单分区（牺牲并行度，极少用）。

### Q8 消费积压 lag 排查处理？
定位：`kafka-consumer-groups.sh --describe --group 组名` 看 CURRENT-LAG。
先区分生产过快还是消费过慢。处理：① 同组加消费者（上限=分区数）② 消费逻辑优化（批处理/异步化/去慢 IO）③ 扩分区（只对新消息生效）④ 下游提并行度 ⑤ 排查频繁 rebalance/GC/外部依赖慢。

### Q9 leader/follower/ISR/LEO/HW？
- leader：分区唯一读写节点；follower：只拉同步不接请求
- ISR：与 leader 保持同步的副本集合（含 leader），落后超阈值踢出
- LEO：每个副本下一条待写入的 offset
- HW：ISR 内最小 LEO；消费者只能读到 HW 以下（保证已同步可见）

### Q10 分区规划？
分区数 ≥ 下游消费者/Flink Source 并行度需求；分区过多有句柄/内存/选举成本，不是越多越好；分区只加不减；key 到分区映射扩容后会变。

## 二、Flink 10 题口述稿

### Q1 三种窗口？
滚动：大小固定不重叠；滑动：大小固定+步长，可重叠（一条数据可能属两个窗口）；会话：按不活跃间隔切，大小不固定。

### Q2 三种时间？
事件时间=数据产生时间；处理时间=Flink 处理时刻；摄入时间=进入 Flink 时刻。
处理时间不感知数据原本发生时刻：数据延迟到达时按处理时间划窗口，会把迟到数据算进"到达时刻"的窗口而非"本应属于"的窗口。

### Q3 Watermark 与触发？
Watermark=水位线信号（表示"事件时间 ≤ 此值的数据都已到达"）。
触发计算：watermark ≥ 窗口结束时间；清窗：watermark ≥ 窗口结束时间 + allowedLateness。

### Q4 迟到数据三层？
① 直接丢弃 ② allowedLateness：窗口触发后再等 N 秒，迟到数据仍可进窗并重新触发计算 ③ 进侧输出流单独收集（对账/补算/警告）。
allowedLateness 期间数据可进窗；窗口彻底清空条件 = watermark ≥ 窗口结束时间 + allowedLateness（非墙钟计时）。

### Q5 状态类型？
- ValueState：单值（累计计数/最新值）
- ListState：元素列表（窗口收集/历史列表）
- MapState：KV 映射（去重/分组统计）
状态按 key 隔离（keyed state），参与 Checkpoint 快照容错。

### Q6 端到端 Exactly-Once 三段式？
① Source 端：KafkaSource 的 offset 纳入 Flink 状态随 Checkpoint 快照
② 中间：算子状态（窗口/聚合）与 offset 同一次快照原子写入（barrier 对齐）
③ Sink 端：KafkaSink 两阶段提交（预提交 → 快照完成 → 提交事务；失败回滚）
（Kafka 自身幂等+事务是另一层；Flink 端到端三段配合）

### Q7 重启策略与恢复？
四种：NoRestart、FixedDelay（固定延迟）、FailureRate（故障率）、ExponentialDelay（指数退避）。
恢复：从最近一次成功的 Checkpoint 快照恢复（offset + 状态一起恢复，续读不丢不重）。

### Q8 keyBy 与聚合 + 数据倾斜？
keyBy 按 key 哈希路由，相同 key 必进同一 subtask，所以 Reduce/Sum 并行度可独立设置，正确性靠 key 哈希保证。
倾斜处理：key 加盐打散 + 两阶段聚合（先局部后全局）、热点 key 单独处理、倾斜 join 优化（广播小表/加盐）。

### Q9 Checkpoint vs Savepoint？
Checkpoint：自动定期快照，用于故障自动恢复。
Savepoint：手动触发的快照，用于人工运维（升级/调整并行度/迁移），不是故障恢复机制。

### Q10 背压排查与处理？
定位：Web UI → Job → SubTasks，看每条 edge 的 BackPressured Time，第一条 HIGH 边的**下游**算子是瓶颈。
处理：① 外部存储逐条写慢 → 攒批/批量写/异步 IO ② 数据倾斜 → 加盐+两阶段聚合 ③ 并行度不足/CPU 满 → 瓶颈算子单独提并行度 ④ GC/堆内存 → 调 Heap ⑤ 状态过大 → RocksDB 增量快照。

## 易混淆坑
- offset 是分区内序号，不是 topic 全局
- 处理时间"算错窗口"根因是不感知数据发生时刻
- 清窗条件 = watermark ≥ 窗口结束 + allowedLateness，不是墙钟等待
- 背压瓶颈是 HIGH 边的下游，不是上游
- checkpoint 自动容错 vs savepoint 人工运维
- Kafka 自身事务 ≠ Flink 端到端 Exactly-Once
