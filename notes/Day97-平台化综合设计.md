# Day97 总结笔记：平台化综合设计（模块七收官）

> 日期：2026-11-10 ｜ 模块七：数据平台工程 ｜ 状态：✅ 理论 + 总体架构设计完成

## 一、从"工具堆"到"平台"

前面 11 天各造一个组件：Airflow（调度）、Atlas/DataHub（元数据）、sqlglot/OpenLineage（血缘）、质量规则库+引擎、FastAPI（服务）、安全方案。

**孤岛问题**：血缘不知道调度、质量失败不知道影响谁、服务不知口径来源、权限不知道表在哪。

**平台化 = 围绕同一套元数据实体把组件串起来**，让三条流贯通：

| 流 | 内容 |
|---|---|
| 数据流 | 业务库 → ODS → DWD → DWS → ADS → API/BI |
| 控制流 | 调度触发 → 任务执行 → 质量校验（P0 阻断）→ 重试/告警 |
| 元数据流 | 任务事件、血缘边、质量结果、访问审计 → 回流治理层 |

## 二、五层总体架构

| 层 | 组件 | 职责 |
|---|---|---|
| 1 数据接入 | Python/DataX | 业务库 → ODS |
| 2 存储计算 | MySQL（教学）/ HDFS+Hive+Spark（生产） | 分层落表与计算 |
| 3 调度编排 | Airflow 2.10.3 | DAG 依赖、定时、补数、重试 |
| 4 数据治理 | 元数据 DataHub / 血缘 sqlglot+OpenLineage / 质量规则库 / 安全 RLS+CLS | 可发现、可追溯、可信、可控 |
| 5 数据服务 | FastAPI + BI | 指标查询、鉴权、脱敏、看板 |

横向：监控告警、成本治理、运维备份。

## 三、元数据是平台骨架

四个组件都依赖同一套实体（表/字段/任务/指标/分级标签）：

- **血缘**：写边（source→target），支撑影响分析
- **质量**：失败规则挂到表实体，算出下游影响
- **权限**：读分级标签生成 RLS/CLS 策略
- **服务**：查表位置、口径、owner、分级

→ 没有元数据，五个组件就是五个孤岛。

## 四、一次日调度的组件协作（时间线）

```
01:00 Scheduler 生成 DagRun → 派发 TaskInstance
 ods_extract  → 抽数（访问留审计）→ 登记 ods_order
 dwd_transform → 执行 SQL → sqlglot 解析血缘写元数据 → 落 dwd_order_detail
 dws_aggregate / ads_report → 持续补血缘边
 quality_check → 读规则库执行 → 结果落表 → P0 失败则 FAIL 阻断下游
 ads_export → 完成后 DagRun 状态回写 → WebUI/告警
 API 服务层读 ADS（只读账号）→ 每次调用写审计
```

## 五、四条关键契约

1. **质量是 DAG 内的 task**，不是旁挂——P0 失败靠任务失败阻断下游（不能"跑完再查"）
2. **血缘双通道**：静态 SQL 解析（提交时/CI，快但只覆盖 SQL 任务）+ 执行侧事件（运行时，全但侵入引擎、没跑就没血缘）
3. **元数据是中枢**：所有组件共用同一套实体
4. **服务层只读 ADS、只走 API**：口径固化、性能保护、权限可控、可审计

## 六、三大架构决策（ADR）

| 决策 | 结论 | 核心理由 |
|---|---|---|
| 调度选型 | Airflow | Python 栈、DAG 即代码可版本化；DS 偏可视化，xxl-job 表达不了 DAG |
| 元数据选型 | DataHub | 多源连接器、UI 可搜索、事件模型；Atlas 重且偏 Hive 合规 |
| 服务层是否直连 DWD | 只读 ADS + API | 口径固化、性能保护、权限可控、可审计 |

## 七、今日小测试（5 题全过）

1. 五层架构 + 三条流 ✅
2. 元数据是骨架，三个依赖组件（补正：Airflow 是"推事件"，真正读写实体的是血缘/质量/权限/服务）✅
3. 质量必须做成 DAG task，P0 阻断下游 ✅
4. 血缘双通道及盲区 ✅
5. 服务层不直连 DWD 的四个理由 ✅

## 八、易混淆坑

- 平台 ≠ 组件的简单相加，关键是**共用一套元数据**
- 质量旁挂 = 没有阻断能力
- 血缘只有静态解析会静默漏边（非 SQL 任务）
- 服务层直连明细 = 账号扩散 + 口径失控 + 性能风险
- "元数据平台"和"调度平台的 Metadata DB"不是一回事：前者管数据资产，后者管任务运行状态
