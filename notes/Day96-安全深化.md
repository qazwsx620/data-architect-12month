# Day96 总结笔记：安全深化

> 日期：2026-11-09 ｜ 模块七：数据平台工程 ｜ 状态：✅ 理论 + 安全方案设计完成

## 一、数仓安全五件套（面试主线）

**分类分级是主线**：先按敏感度给数据打标（公开 / 内部 / 敏感 PII / 机密），再配套四件事：

| 组件 | 作用 |
|---|---|
| 权限 | 表级（能不能看表）、行级（能看哪些行）、字段级（能看哪些列） |
| 脱敏 | 展示形态处理（掩码/哈希/泛化/置空），不可逆 |
| 加密 | 传输 TLS、存储 TDE、字段 AES-256 + KMS 管密钥，可逆 |
| 审计 | 六要素留痕、不可篡改、保留 ≥6 个月、异常告警 |

分级决定：谁能看（权限）、看到什么形态（脱敏）、存成什么样（加密）、留多久（生命周期）。

## 二、行级权限（RLS）

场景：同一张表，不同角色只能看自己的行。

| 环境 | 实现 |
|---|---|
| Hive/Spark | Ranger 行过滤策略（查询时自动注入条件） |
| MySQL | 视图 + 授权（每部门一个带 WHERE 的视图；MySQL 原生无 RLS） |
| 数仓/API 层 | 服务端按身份解析注入过滤条件 |
| 云平台 | MaxCompute 行级权限 / Snowflake Row Access Policy |

设计要点：
- 规则**集中配置**（用户/角色 → 可见行条件）
- **服务端注入**，绝不接受调用方传 `region` 参数（可伪造 = 越权漏洞）
- **默认拒绝**（没配就是无权）
- 多租户用 `org_id/tenant_id` 隔离
- **行列叠加**：先 RLS 过滤行，再 CLS 脱敏列

难点：性能（过滤字段要有索引/分区）、权限变更即时生效、审计留痕。

案例：`dwd_order_detail` 没有 region 字段，运营行过滤要靠 `user_id IN (SELECT user_id FROM dim_user WHERE region='华东')`；而 `dim_user` 自身直接配条件 `region='华东'`。

## 三、字段级权限（CLS）与脱敏

| 方式 | 做法 |
|---|---|
| 列掩码（Ranger Column Masking） | 按用户/组配置列的返回形态 |
| 视图拆分 | 对外视图替换敏感列，只授视图权限 |
| API 层脱敏 | 返回前按角色改写字段（Day91 服务层） |

脱敏策略：掩码 `138****1234`、哈希（可 join 不可还原）、截断/泛化（地址→城市）、置空 NULL。

## 四、加密

| 层级 | 做法 | 说明 |
|---|---|---|
| 传输 | TLS/SSL | 客户端↔DB、跨机房同步 |
| 存储 | 磁盘加密 / TDE / HDFS Transparent Encryption | 防物理盘丢失 |
| 字段 | 应用层 AES-256 入库 | 最敏感字段（身份证、银行卡） |
| 密钥 | KMS 集中管理 + 轮换 | 密钥绝不与密文同放 |

**脱敏 vs 加密**：脱敏不可逆（给人看），加密可逆（给还原）；字段加密后 LIKE/范围查询失效（索引无效、密文无序），要检索需另建哈希列。

## 五、审计日志

**六要素**：谁 / 何时 / 对什么（库表字段）/ 做了什么（操作+SQL）/ 结果（成功·失败·拒绝）/ 从哪来（IP/客户端）。

**采集点**：数据库审计插件、Ranger Audit、API 网关、平台操作日志。

**管理四件事**：集中存储（append-only 不可篡改）→ 保留期（等保 ≥6 个月）→ 异常告警（大批量导出/非工作时间/敏感表高频/**deny 越权尝试**）→ 定期审计报告（僵尸权限清理）。

**审计 ≠ 运行日志**：审计不可篡改、长期保留、只追加；运行日志可滚动删除。

坑：只记成功 = 漏掉越权信号；SQL 全文含敏感值进日志 = 二次泄露；采样丢日志 = 审计无效。

## 六、实操：数仓安全方案（scripts/day96/数仓安全方案.md）

三张表：角色 × 表行级矩阵、角色 × 敏感字段列级矩阵、加密决策表。

**行级矩阵**：

| 角色 | dwd_order_detail | dim_user | ads_gmv_report |
|---|---|---|---|
| ETL 开发 | 全量 | 全量 | 全量 |
| 数据分析师 | 全量 | 全量行 | 全量 |

| 华南运营 | 同上（华南） | `region='华南'` | 本区域聚合 |
| 财务 | 全量 | 全量行（PII 全置空，可考虑不给） | 全量 |
| 外部 BI | 无权 | 无权 | 全量（对外视图+鉴权+限流） |

**字段级矩阵（dim_user）**：

| 角色 | phone | address | id_card | user_name |
|---|---|---|---|---|
| ETL 开发 | 全量 | 全量 | 全量 | 全量 |
| 数据分析师 | 掩码 | 城市级泛化 | 置空 | 可看 |
| 华东/华南运营 | 掩码 | 城市级泛化 | 无权 | 可看 |
| 财务 | 无权 | 无权 | 无权 | 可看 |

## 七、面试答案

**数仓安全包含什么**：分类分级为主线 + 权限（表/行/列）+ 脱敏 + 加密（传输/存储/字段）+ 审计；落地载体 Ranger/视图/API，每次访问留痕。

**行级权限怎么做**：查询入口按身份注入行过滤条件（Ranger row filter / 视图 / 服务端注入），规则集中配置、默认拒绝、拒绝调用方传参。

## 八、易混淆坑

- 行级 vs 表级权限（能看哪些行 vs 能不能看表）
- 字段级权限 vs 脱敏（能不能看这列 vs 看到什么形态）
- 脱敏 vs 加密（不可逆展示 vs 可逆还原）
- 业务系统权限 ≠ 数仓分析权限（精确触达走业务系统单次授权）
- 只记成功日志 = 漏掉越权信号；审计日志可改 = 没有审计
- 财务类角色：数据敏感度高但 PII 需求低（金额全给、身份全不给）
- SQL 字符串用单引号；权限配置写"条件表达式"，不写整条 SELECT
