## 一、调度平台高频题

**Q1 为什么选 Airflow**（四步法：场景→需求→对比→结论）
> 四层依赖（ODS→DWD→DWS→ADS）+ 上游失败阻断 + 重试 + 补数 = DAG 编排能力；Python 栈、要代码版本化；xxl-job 表达不了 DAG，DS 偏 Java+可视化配置 → Airflow。

**Q2 Airflow 架构**
> Scheduler（读 DAG、建 DagRun、派发 TaskInstance）+ Executor/Worker（执行）+ WebUI + Metadata DB（存运行状态）。主线：读定义→建 Run→派发→执行→回写→展示。

**Q3 DAG 为什么无环**
> 有环即循环依赖，调度器无法拓扑排序，任务永远等不到前置完成 → 死锁。

**Q4 失败处理**
> 自动重试（retries+retry_delay）→ 超限告警 → 人工介入；补数按历史区间重跑；**重跑与补数都必须幂等**（INSERT OVERWRITE 分区覆盖 / upsert），禁止 INSERT INTO 追加。

**Q5 幂等手段**
> 覆盖写（Hive 按 dt 分区 OVERWRITE、MySQL REPLACE/ON DUPLICATE KEY UPDATE）+ 状态判断（目标分区存在则重建或跳过）。

**Q6 补数**
> Airflow backfill / 手动触发指定逻辑日期；按天串行、幂等、限并发。

**坑**：schedule_interval ≠ start_date；重试 ≠ 补数；LocalExecutor 只适合单机；补数按 logical date。

## 二、元数据平台高频题

**Q1 元数据三类**
> 技术（库表字段/分区/存储/任务/SQL）、业务（含义/口径/owner/主题域/分级）、管理（权限/访问/生命周期/质量分）。

**Q2 采集**
> Pull（Crawler 扫库）→ 技术元数据；Push（Hook/API/表单）→ 业务元数据。只 Pull 会缺业务元数据与 owner/口径。

**Q3 Atlas vs DataHub**
> Hive/HBase 重度、强合规分级 → Atlas；多源异构（MySQL/Spark/云）、要现代可搜索 UI → DataHub。

**Q4 价值**
> 找得到（搜索）、看得懂（业务含义/owner）、追得到（血缘/影响分析）、管得住（分级/权限）、算得清（成本/热度）。

**Q5 元数据滞后**
> 自动采集高频 + 变更审批联动登记 + 责任到人（核心表必须有 owner）+ 准确率进大盘。

**坑**：元数据 ≠ 数据字典；调度 Metadata DB ≠ 元数据平台；Atlas 分类标签 ≠ 权限。

## 三、血缘高频题

**Q1 表级 vs 字段级**
> 表级 A→B（影响分析），字段级 A.a→B.b（口径/问题定位/脱敏）。先表级，核心表补字段级。

**Q2 两条路线**
> 解析侧：SQL→AST 提 target/source，无需运行可进 CI；盲区=动态 SQL、变量拼名、多方言、只覆盖有 SQL 的任务。
> 执行侧：Hive Hook/Spark Listener/OpenLineage 运行态采集；盲区=侵入引擎、只采跑过的、换引擎重接。

**Q3 为什么漏边（实测）**
> 自动解析 3 条，手工 8 条，漏的 5 条全是非 SQL 任务（Python 抽取、维表加载、文件导出）→ 需非 SQL 任务显式登记 read/write，或执行侧 Hook 补。

**Q4 CTE/子查询/UNION**
> CTE 是逻辑表名要穿透；子查询/UNION 每个分支都要遍历；sqlglot 可做（AST），sqlparse 只分词不是血缘解析器。

**Q5 用途**
> 影响分析、故障定位（找上游根因）、成本归因、合规（PII 扩散/删除请求）。

**Q6 OpenLineage**
> 血缘事件规范（job/run/dataset），后端 Marquez/DataHub 接收，跨引擎统一。

**坑**：解析成功 ≠ 血缘正确；血缘有环 ≠ 数据有环；血缘"全量"是伪命题，要监控覆盖率。

## 四、数据服务高频题

**Q1 为什么要有服务层**
> 直连四问题：账号扩散、口径不一、性能冲击、不可观测。服务层：解耦、口径固化、安全可控、性能保护。

**Q2 API 四要素**
> ① 查询服务（版本化路径、参数校验含范围上限、SQL 参数化、只读账号、超时、统一返回）
> ② 权限三层（认证 API Key/JWT → 授权 RBAC+脱敏 → 审计）
> ③ 限流（令牌桶/漏桶/配额，超限 429 + Retry-After）
> ④ 缓存（Redis+TTL，防穿透/击穿/雪崩）

**Q3 认证/授权/审计**
> 认证=你是谁（401）；授权=你能干什么（403）；审计=你干了什么。认证通过 ≠ 有权限。

**Q4 缓存三问题**
> 穿透→布隆过滤器/空值缓存；击穿→互斥锁/热点不过期；雪崩→TTL 随机抖动/多级缓存。

**Q5 SLA**
> 入口限流鉴权、查询只读+参数上限+超时、数据预聚合物化、监控 P95/P99+错误率、降级返回缓存。

**坑**：限流 ≠ 熔断；直连 ADS 仍需 API 管控；一致性要求高的场景（对账）不上缓存。
