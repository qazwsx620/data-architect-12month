## 1. 表锁 vs 行锁

| | 表锁 | 行锁 |
|--|------|------|
| 锁粒度 | 整张表 | 单行记录 |
| 并发度 | 低 | 高 |
| 开销 | 小 | 大（维护锁信息） |
| 死锁 | 不会 | 可能 |
| 典型引擎 | MyISAM | InnoDB |

> InnoDB 默认行锁；MyISAM 只有表锁。

## 2. 行锁两种模式（面试必背）

1. **共享锁 S锁（读锁）**：`SELECT ... LOCK IN SHARE MODE`
   可多个事务同时持有，只读不写
2. **排他锁 X锁（写锁）**：`SELECT ... FOR UPDATE` / UPDATE / DELETE / INSERT
   独占，持有期间其他事务不能读也不能写

**锁兼容性**：
- S-S：兼容（可同时读）
- S-X：不兼容（读阻塞写、写阻塞读）
- X-X：不兼容（写写互斥）

## 3. 实操验证：X锁阻塞当前读（实测）

```
A: BEGIN; SELECT * FROM account WHERE name='张三' FOR UPDATE;   -- 持X锁
B: 普通 SELECT（快照读）→ 立即返回（MVCC 不阻塞）
B: SELECT ... FOR UPDATE（当前读）→ 卡住等待
A: COMMIT → B 的 FOR UPDATE 返回
```
> 结论：X锁阻塞其他事务的当前读和写，但不阻塞快照读（普通SELECT靠MVCC）。

## 4. 三种锁范围

| 锁 | 锁什么 | 作用 |
|----|--------|------|
| 记录锁 Record Lock | 单行记录本身 | 锁行 |
| 间隙锁 Gap Lock | 行之间的间隙 | 只防插入 |
| 临键锁 Next-Key Lock | 当前行+前面间隙 | 记录锁+间隙锁组合，InnoDB默认 |

> 防幻读原理：REPEATABLE READ 下间隙锁禁止其他事务在间隙插入新行。
> 例子：id=1、5、10，临键锁锁 `(-∞,1]、(1,5]、(5,10]、(10,+∞)`。

## 5. 死锁

**定义**：两个事务互相持有对方需要的锁，循环等待，谁也执行不下去。

**经典场景**：
```
A: 持有行1锁 → 想更新行2（等B）
B: 持有行2锁 → 想更新行1（等A）→ 死锁
```

**InnoDB 处理**：
1. 死锁检测：自动回滚其中一个事务（牺牲者），释放其锁
2. 报错：`ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`
3. 业务代码捕获异常后重试

**预防（开发规范）**：
1. 按固定顺序访问资源（都先更新行1再行2）
2. 尽量缩短事务时间，减少锁持有时间
3. 避免大范围锁，减少不必要 FOR UPDATE
4. 捕获死锁异常后重试事务

## 6. 运维查看锁/事务

```sql
SELECT trx_id, trx_state FROM information_schema.innodb_trx;
SHOW ENGINE INNODB STATUS;   -- 查看最近死锁信息
```

## 踩坑记录（面试素材）
- 以为 X锁阻塞所有读 → 快照读靠 MVCC 不阻塞，只阻塞当前读
- 死锁复现顺序：两条 UPDATE 必须交叉才死锁
- 忘记死锁重试 → 业务需捕获 1213 异常重试
- 间隙锁范围理解错 → 锁的是区间，不是具体行
- 实验残留事务 → 收尾 COMMIT + innodb_trx 检查
