# Day76 · 双链对账 / Lambda-Kappa（架构选型 + 对账机制）

> 模块六 · 实时数仓实战 Day9 | 配套脚本见 `scripts/day76/`（reconcile_check.py + README）。
> 真实环境：离线 ads_gmv_report(10-12=59) vs 实时 GMV=59 → 对账通过，口径 status=2 对齐。

---

## 1. Lambda 架构（实时 + 离线双链路）

```text
双链路并行：
  实时链路：Flink → 秒级结果（快，但窗口近似，可能不准）
  离线链路：Spark/Hive → T+1 准确结果（慢，但可重跑、准确）
结果按需合并/对账

优点：既快又准（实时快 + 离线兜底）
缺点：两套代码、两套口径，维护成本高
```

## 2. Kappa 架构（纯实时单链路）

```text
只有一条流式链路（Flink）
重算靠 Kafka 重放：offset 从头读 → 重新跑一遍流 → 修正结果
（Kafka 数据可重放 = Kappa 能"重跑"的根基）

优点：一套代码一套口径，运维简单
缺点：复杂批量计算/历史回溯能力弱，全量重放成本高
```

## 3. 双链对账（可靠性核心）

```text
为什么对账：实时结果（近似）≠ 离线结果（准确）是常态
  → 定时比对两边同一指标（如 5 分钟/天级）
  → 差异超阈值 → 告警排查
  差异常见来源：窗口近似 / 数据延迟 / 丢数据 / 过滤口径错

前提：口径统一（GMV 都用 status=2）
  → 口径不一致时对账全是噪音
```

## 4. 实操：双链对账（reconcile_check.py）

```text
离线链路：MySQL 查 ads_gmv_report（权威，10-12=59，status=2 口径）
实时链路：RealTimeGmv 输入 2001,59,2 → 实时 GMV=59
对账：reconcile_check.py 比对 59 vs 59 → [通过]（口径 status=2）
若实时=59、离线=118 → [告警]，优先排查实时链路（丢数据/窗口/过滤）
```

## 今日面试考点清单
1. Lambda 双链路？→ 离线+实时，两套维护贵
2. Kappa 重算靠什么？→ Kafka 重放，重算贵
3. 为什么对账？→ 实时近似≠离线准确，差异超阈值告警
4. 对账前提？→ 口径统一，否则全是噪音
5. 差异怎么排查？→ 实时优先（丢数据/窗口/过滤）

## 易混淆坑
- Lambda≠Kappa：双套 vs 单套，不是"谁好谁坏"，按场景选
- Kappa"重放"依赖 Kafka 数据保留期（retention），不是无限回溯
- 对账是"抓差异"，不是"证明实时准"
- 口径不统一的差异是噪音，先统一口径再对账
