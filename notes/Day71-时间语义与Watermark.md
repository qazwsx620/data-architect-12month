# Day71 · 时间语义与 Watermark（事件时间 + 乱序 + 触发机制）

> 模块六 · 实时数仓实战 Day4 | 配套脚本见 `scripts/day71/`（EventTimeWindow.java）。
> 真实环境：Flink 1.19.1，socket 乱序订单流 → 事件时间窗口 + Watermark 跑通。

---

## 1. 三种时间语义（面试必答）

| 时间 | 含义 | 说明 |
|------|------|------|
| 事件时间 Event Time | 数据**产生**的时间（业务时间） | 生产最常用 |
| 处理时间 Processing Time | Flink **处理**该数据的机器时间 | 简单但不可靠 |
| 摄入时间 Ingestion Time | 数据**进入 Flink** 的时间 | 介于两者 |

> 为什么用事件时间：处理时间在数据延迟时会算错窗口（23:59:50 的订单 00:00:10 才到，处理时间会算进 00:00 窗口）。

## 2. 乱序 + Watermark（核心）

```text
乱序：网络/上游延迟 → 到达顺序 ≠ 事件时间顺序

Watermark = 时间水位线信号："事件时间 ≤ Watermark 的数据我都收到了"
计算：Watermark = 最大已见事件时间 - 允许乱序（如 3s）
触发：Watermark ≥ 窗口结束时间 才触发（先等乱序数据）
```

## 3. 实操：事件时间窗口 + Watermark（EventTimeWindow.java）

```java
// 指定事件时间 + 允许乱序 3s
WatermarkStrategy
    .<Tuple3<Integer, Double, Long>>forBoundedOutOfOrderness(Duration.ofSeconds(3))
    .withTimestampAssigner((e, t) -> e.f2);   // f2 = 事件时间（毫秒）

// 10s 滚动事件时间窗口
TumblingEventTimeWindows.of(Time.seconds(10))
```

### 实测：乱序输入
```
1,2999,10000      # [10000,20000)
2,99,11000        # [10000,20000)
3,118,8000        # ← 乱序：事件时间 8s 最后到，正确归 [0,10000)
4,399,14000       # [10000,20000)
5,59,13000        # [10000,20000)
6,5000,16000      # 事件时间 16s → Watermark=13s，仍未触发 [10000,20000)
7,8888,23000      # 事件时间 23s → Watermark=20s ≥ 20000 → 触发 [10000,20000)
```

### 输出
```text
窗口[0~10000) 订单数=1 金额=118.0        ← 8000 乱序单正确归窗
窗口[10000~20000) 订单数=5 金额=8556.0   ← 2999+99+399+59+5000（不含 8000）
```

## 4. 核心逻辑（面试可手写讲解）
8000ms 数据到达时 Watermark 还没到 10000 → [0,10000) 窗口**尚未触发** → 它仍能进该窗；判断依据是"到达时窗口是否已触发"，不是数据本身大小。

## 易混淆坑
- Watermark 是动态推进的（随最大事件时间走），不是固定值
- "迟到能进窗"取决于到达时窗口是否已触发
- 事件时间窗口必须配 Watermark 才有意义
