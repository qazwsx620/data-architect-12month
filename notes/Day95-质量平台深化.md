# Day95 总结笔记：质量平台深化

> 日期：2026-11-09 ｜ 模块七：数据平台工程 ｜ 状态：✅ 理论 + 质量平台雏形实测通过

## 一、质量监控大盘

五类核心指标：

| 指标 | 作用 |
|---|---|
| 规则通过率 | 整体健康度（按天/表/类型） |
| 失败规则 Top N | 定位高频问题 |
| 影响范围 | 失败规则影响的下游表/任务（靠血缘） |
| 趋势 | 近 7/30 天通过率曲线 |
| 告警时效 MTTR | 告警产生到处理完成的时长 |

设计要点：结果**必须落库/落文件**（每次执行一行：run_date/table/rule_id/status/value/threshold）；大盘读**结果表**，不直连业务库；失败可下钻到字段和样例；还要看**规则覆盖度**（多少表没配规则）。

## 二、规则管理（配置化进阶）

**规则模型字段**：规则 ID、目标（表/字段）、规则类型（完整性/唯一性/值域/及时性/一致性/准确性/自定义 SQL）、表达式/参数、阈值、级别、调度依赖、负责人/通知渠道、启用状态。

**分级处置**：
- P0 → 阻断下游（DAG quality_check 失败即停）
- P1 → 告警，下游继续
- P2 → 只进大盘

**规则模板**：非空、主键唯一、行数波动、金额非负、分区存在、跨表对账——模板+参数实例化。

**治理**：阈值变更记录版本+评审（防"调宽阈值掩盖问题"）；清理僵尸规则；按覆盖度评估（核心表必须有主键/非空/及时性规则）。

## 三、告警闭环

四环节：**触发（带上下文：表/规则/实际值 vs 阈值/样例/影响）→ 分级通知 → 认领处理 → 恢复确认关闭 → 复盘**。

三机制：
- **去重/抑制**：同一规则连续失败合并一条，按状态更新
- **升级**：超时未处理自动升级（上级/值班）
- **收敛**：同一根因导致多条规则失败，合并为一个事件（结合血缘找共同上游）

工单联动：P0/P1 自动建单，状态与告警联动，MTTR 进大盘。

## 五、踩坑记录（三个真实错误）

1. **规则 SQL 字段名与表结构不符**：`pay_amount`（实为 `amount`）、`dt`（实为 `order_date`）→ 引擎直接 `1054 Unknown column` 崩溃，不是判失败
2. **函数缺括号**：`CURDATE` 写成列名 → `Unknown column 'CURDATE'`
3. **假绿灯**：R004 及时性写成 `<= 0`，没数据也 PASS——规则方向/阈值错误比误报更危险

## 六、面试答案

**质量平台怎么设计**：规则库（配置化）→ 执行引擎（结果落表）→ 监控大盘（通过率/Top/影响/趋势/MTTR）→ 告警闭环（分级/工单/恢复确认）；质量任务挂 ETL 后，P0 阻断下游。
**规则怎么管**：规则库+模板+分级+版本评审+覆盖度治理。
**告警怎么闭环**：触发（带上下文）→ 分级通知 → 认领处理 → 恢复确认关闭 → 复盘；配去重/升级/收敛。

## 八、易混淆坑

- 假绿灯（规则方向错）比误报更危险
- 规则 SQL 写错字段是引擎崩溃，不是 FAIL
- 规则多 ≠ 质量好，看核心表覆盖度
- 告警 ≠ 闭环：要有处理结果和恢复确认
- 大盘读结果表，不直连业务库
