## 1. 事实表三类型（面试骨架题）

| 类型 | 一行代表什么 | 特点 | 适用 |
|------|-------------|------|------|
| 事务事实表 | 一次事件/一笔交易 | 最细粒度，可累加 | 订单、支付流水、点击日志 |
| 周期快照事实表 | 某周期末的状态 | 周期汇总快照 | 每日库存、每日账户余额 |
| 累积快照事实表 | 一个业务流程的完整生命周期 | 记录各阶段时间/状态 | 订单下单→支付→发货→完成 |

### 选型（一句话）
```text
关注"发生了多少" → 事务事实表
关注"某时刻剩多少/是多少" → 周期快照
关注"一个流程走多久/到哪步" → 累积快照
```
> 模块四对应：`fact_order`（事务，一单一单）/ `dws_user_daily`（周期快照，一天一用户）。

## 2. 退化维度（面试易混淆点）

**不建维度表、直接放事实表的维度**——典型是订单号 order_id：每单只有一个、无独立属性，建"订单维度表"属于"主键当外键"的无意义建模。

```text
正常：fact_order.user_id → dim_user.user_id（外键关联维度表）
退化：fact_order.order_id 直接放（不建 dim_order）
```

## 3. 一致性维度（解决"数字对不上"）

**一套维度表被所有事实表共享复用** → 跨表关联用户维/商品维是同一份 → 各团队报表对得上。

反例：各团队各建一套用户维表 → "用户数对不上"。

## 4. 实操②：退化维度识别（模块四 fact_order）

```sql
DESC fact_order;
-- order_id: PRI（业务主键，退化维度）
-- user_id / product_id: 外键维度
```

## 5. 实操③：一致性维度验证（踩坑实录）

### 坑：维度表空表 → join 全 NULL
模块四只建了 dim_user/dim_product，**没灌维度数据** → LEFT JOIN 结果 user_name/product_name 全 NULL。

> 面试素材：**事实表 join 维度表全 NULL 排查：① 先看维度表是否有数据；② 再看 ID 是否匹配**。

### 修复：灌入维度数据
```sql
INSERT INTO dim_user (user_id, user_name) VALUES
  (1001,'张三丰'),(1002,'李四'),(1003,'王五'),(1004,'赵六'),(1005,'钱七'),
  (1006,'孙八'),(1007,'周九');
INSERT INTO dim_product (product_id, product_name) VALUES
  (2001,'手机'),(2002,'笔记本'),(2003,'耳机'),(2004,'键盘'),(2005,'鼠标');
```

### 修复后验证结果
- 用户维：张三丰 8998（两单合计）、赵六 399、周九 399、王五 118、孙八 59
- 商品维：笔记本 5999、手机 2999、鼠标 798（两日）、键盘 177（两日）

## 今日面试考点清单
1. 三种事实表？→ 事务一单一行 / 周期快照一天一用户 / 累积快照一流程一行
2. 选型？→ 发生多少 vs 剩多少 vs 流程进度
3. 退化维度？→ 不建表直接放事实表（order_id）
4. 一致性维度？→ 一套维表多事实表复用，跨表口径一致
5. join 全 NULL 排查？→ ① 维度表有无数据 ② ID 是否匹配

## 易混淆坑
- 周期快照存的是"状态/汇总"，不是事件明细
- 退化维度 ≠ 外键维度（退化：无属性不建表；外键：有独立维度表）
- LEFT JOIN 全 NULL 先怀疑维度表空，不是 join 写错
- 一致性维度是"共享同一套"，不是"各自建一套"
