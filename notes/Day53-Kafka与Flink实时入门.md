## 1. Kafka 与消息队列

### 为什么需要 Kafka
业务系统每下一单就要"告诉"数仓。直接写数据库扛不住高并发；轮询拉取实时性差。**Kafka = 消息高速公路**：业务把消息丢上去，消费者按需取，**解耦 + 削峰**。

### 核心概念（面试必答）
| 概念 | 含义 | 类比 |
|------|------|------|
| Topic | 消息分类（如 order_topic） | 车道 |
| Partition | Topic 分多个分区 | 并行道 |
| Producer | 生产消息 | 往道发消息 |
| Consumer | 消费消息 | 从道收消息 |
| Consumer Group | 一组消费者协同消费 | 分工收货 |

### Kafka 为什么快（高频）
1. **顺序写磁盘**：追加写日志，不用随机寻址
2. **分区并行**：多分区多消费者并行
3. **批量/压缩**：攒批发送，减少网络开销

> 一句话：顺序写盘 + 分区并行 + 批量压缩。

## 2. Flink 与流处理

### 批处理 vs 流处理（面试必答）
| | 批处理（离线） | 流处理（实时） |
|--|---------------|---------------|
| 处理单位 | 一批数据 | 一条一条来 |
| 延迟 | 分钟~小时 | 秒级 |
| 代表 | Spark/Hive | Flink |
| 场景 | 日报/月报 | 实时大屏/风控 |

### Flink 核心概念
| 概念 | 含义 |
|------|------|
| 流 Stream | 源源不断的数据事件 |
| 窗口 Window | 无限流切有限批（每5分钟/每天） |
| 事件时间 | 数据真实发生时间（vs 处理时间=到达时间） |
| 状态 | 跨事件记忆（累加器） |

> 面试：窗口 = 把无限流变成有限批；事件时间解决"数据晚到"——按真实发生时间归窗。

## 3. 实时数仓架构（离线 vs 实时）

```
【离线数仓】（Day47-52 已落地）
业务库 → ODS → DWD → DWS → ADS → 日报表（T+1，每天凌晨跑，看昨天）

【实时数仓】（概念版）
业务库/日志 → Kafka（消息接入）→ Flink（实时清洗/聚合）→ 实时DWS/ADS → 实时大屏（秒级，看当下）
```

## 4. 实时订单数仓设计（实操③）

1. 订单消息 → Kafka `order_topic`（按订单ID哈希选分区，保序）
2. Flink 消费 → 清洗（复用离线映射：status→可读）+ 窗口聚合（5分钟/小时 GMV）
3. 实时报表：实时 GMV/订单量/客单价，延迟秒级

## 5. Kafka/Flink 概念对比表（实操①）

| 维度 | Kafka | Flink |
|------|-------|-------|
| 定位 | 消息中间件（传输） | 流计算引擎（计算） |
| 角色 | 存转发消息 | 实时处理计算 |
| 核心概念 | Topic/Partition/Producer/Consumer | 流/窗口/事件时间/状态 |
| 典型用法 | 数据接入、解耦 | 实时聚合、实时报表 |

1. Kafka 4 核心概念？→ Topic/Partition/Producer/Consumer
2. Kafka 为什么快？→ 顺序写盘+分区并行+批量压缩

## 易混淆坑（面试素材）
- Kafka 是传输工具，Flink 是计算工具，不是一个东西
- 事件时间 vs 处理时间：晚到的数据要按真实发生时间归窗
- Consumer 和 Consumer Group：单消费者 vs 多消费者协同
- 离线看"昨天"，实时看"当下"——T+1 vs 秒级
