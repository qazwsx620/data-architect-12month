## 1. 为什么实时 Join 维表比离线难（面试必答）

```text
离线：Hive 表 JOIN 维表 = 一条 SQL，全量表碰一次，无 IO 负担
实时：流是一条条来的，维表数据【不在流里】
  → 每条数据都要查外部维表（MySQL/HBase/Redis）→ 外部 IO 是瓶颈
```

## 2. 生产维表关联三件套（面试必答）

```text
① 加载维表到内存缓存：查一次 → 缓存进本地状态（MapState/缓存）→ 少查库
② 异步 IO（Async I/O）：异步并发查 MySQL 维表，不阻塞主线程 → 吞吐提升
③ 广播流（Broadcast）：维表变更进广播流 → 各并行子任务实时更新缓存
   （不重启作业）

维表变更策略：缓存 TTL / 版本号比对 / 广播更新
```

## 3. 实时 Join vs 离线 Join

| 维度 | 离线 Join | 实时 Join |
|------|-----------|-----------|
| 方式 | 全量表 JOIN 一次 | 每条流数据查维表 |
| 瓶颈 | 无 IO 负担 | 外部 IO（缓存/异步解决） |
| 维表 | 取快照即可 | 数据会变，需更新策略 |

## 4. 实操：DimJoinDemo.java（订单关联用户维度）

```java
// 教学简化：内存 Map 模拟 MySQL dim_user（1→张三 2→李四 3→王五）
// 生产：MySQL/HBase + 异步IO + 缓存(TTL/版本号)/广播流
```

## 5. 维表查不到怎么办（面试必答 2 招）

```text
① 兜底默认值：查不到给"未知"，明细不丢（业务接受未知口径）
② 侧输出流收集：查不到的数据进侧输出流（旁路暂存），维表更新后回补关联
   （未知占比过高 → 排查维表同步延迟）

原则：订单是真实发生的，维表查不到 ≠ 用户不存在（维表同步/数据延迟/脏数据）
```

## 今日面试考点清单
1. 实时 Join 难在哪？→ 维表不在流里，每条都查，IO 瓶颈
2. 三件套？→ 缓存 + 异步 IO + 广播更新
3. 实时 vs 离线 Join？→ 一条 SQL vs 每条查维表
4. 维表变更？→ TTL / 版本号 / 广播
5. 查不到？→ 兜底值 + 侧输出流待补

## 易混淆坑
- 维表查不到 ≠ 丢弃数据（兜底 + 侧输出双保险）
- 广播流解决的是"维表更新"，不是"首次加载"
- 异步 IO 提升的是吞吐，缓存减少的是查询次数（两者配合）
- keyBy 后维表查询才有状态隔离（Keyed State 按用户）
