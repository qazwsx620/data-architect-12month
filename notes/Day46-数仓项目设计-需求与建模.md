## 1. 业务需求梳理（设计第一步）

电商平台，业务库有订单/用户/商品三类数据。数仓要回答：
- **GMV、订单量、客单价**
- **按用户维度**：每用户消费多少、下单频次
- **按商品维度**：每商品卖多少、哪品类最好卖

> 面试：拿到需求 → **先明确业务问题 → 才能定表和粒度**，不是上来就建表。

## 2. 分层表清单（8表）

| 层 | 表名 | 内容 | 粒度 |
|----|------|------|------|
| ODS | ods_order | 订单原始数据（原样+raw_data兜底） | 每订单一行 |
| DIM | dim_user | 用户维度 | 每用户一行 |
| DIM | dim_product | 商品维度 | 每商品一行 |
| FACT | fact_order | 订单事实（外键+可加总指标） | 每订单一行 |
| DWD | dwd_order_detail | 清洗规范化（status转可读） | 每订单一行 |
| DWS | dws_user_daily | 按用户+日期汇总 | 每用户每天一行 |
| DWS | dws_product_daily | 按商品+日期汇总 | 每商品每天一行 |
| ADS | ads_gmv_report | 每日GMV/订单量/客单价 | 每天一行 |

> ODS 和 DWD 都有订单表的原因：
> - ODS 原样保留 → 可追溯，出问题回源头重算
> - DWD 清洗规范化 → 下游复用一套干净数据
> - 并存 = DWD 错了能回 ODS 重跑

## 3. 星型模型

```
          dim_user（用户维度）
                │
dim_product ── fact_order（订单事实）── dim_date（日期维度）
                │
          （金额/数量/状态）
```
- 事实表：**外键 + 可加总指标**
- 维度表：**描述属性**

## 4. 粒度（面试高频）

**粒度 = 一行代表什么**。同一事实不同粒度设计完全不同：
- fact_order：一单一行（订单粒度）→ 看每单明细
- dws_user_daily：一天一用户一行（用户-日粒度）→ 看用户每天消费

> 粒度决定表能回答什么问题：越细越灵活、数据量越大；**先定粒度再建表**。

## 5. 口径（重点！）

**口径 = 指标怎么算的定义**，必须统一，否则各部门数字对不上：

| 指标 | 口径 |
|------|------|
| GMV | 已支付（status=2）订单金额合计 |
| 订单量 | 支付订单笔数 |
| 客单价 | GMV ÷ 订单量 |

> ①业务定义：钱到账才算成交，未支付不是真实 GMV
> ②口径统一：全部门同标准，数字才能对齐
> 口径由**业务方+数据团队**共同定义，写文档，谁改谁负责。

## 6. 命名规范

```
ods_order           = ods层 + order主题
dwd_order_detail    = dwd层 + 明细
dws_user_daily      = dws层 + user主题 + 日粒度
ads_gmv_report      = ads层 + gmv报表
dim_user            = 维度表
```
> 规律：层前缀 + 主题 + 粒度后缀；全小写下划线。看表名知层级内容。

## 踩坑记录（面试素材）
- 需求没定就建表 → 表建了不能用
- 口径不统一 → GMV 各部门对不上，返工
- 粒度没定义 → 汇总表改来改去
- ODS 不留原样 → 出问题无法回溯
- 命名随意 → 看表名不知道是哪层
