## 1. 主从复制原理

主库（Master）负责写，从库（Slave）负责读，数据变更实时同步。

### binlog（二进制日志）
主库开启 binlog，记录所有修改数据的操作（UPDATE/INSERT/DELETE/DDL），是复制的数据源。

```sql
SHOW VARIABLES LIKE 'log_bin';      -- ON 开启
SHOW MASTER STATUS;                 -- 当前 binlog 文件与位置
```

### 复制流程：三个角色（面试必背）
```
主库 dump线程 → 发binlog → 从库 IO线程 → 写入 relay log → 从库 SQL线程 → 重放 → 数据同步
```
1. **主库 dump线程**：收到从库请求，读取 binlog 发送给从库（每从库独立一个）
2. **从库 IO线程**：连接主库拉取 binlog，写入 relay log（中继日志）
3. **从库 SQL线程**：读取 relay log 重放执行，应用到从库

> 面试一句话：主库写 binlog，从库 IO 线程拉日志存 relay log，SQL 线程重放完成同步。

### 从库过多的问题
每个从库一个 dump 线程，从库太多会给主库带来压力 → 级联复制（主→从→从）缓解。

## 2. 读写分离

- 写走主库（一致性），读走从库（分摊压力）
- **主从同步延迟**：刚写入主库的数据，从库可能未同步，立刻读从库读不到
- 解决：关键数据强制读主库、非关键数据延迟容忍、半同步复制、监控延迟

## 3. 完整配置流程（口述版）

```
1. 主库：开启 binlog + 配置 server-id（全局唯一）
2. 主库：创建复制账号，授权 REPLICATION SLAVE
3. 从库：配置不同的 server-id
4. 从库：CHANGE MASTER TO 指定主库地址/账号/binlog文件+位置
5. 从库：START SLAVE
6. 验证：SHOW SLAVE STATUS → Slave_IO_Running / Slave_SQL_Running 都 YES
```

```sql
SHOW VARIABLES LIKE 'server_id';
SHOW VARIABLES LIKE 'binlog_format';   -- ROW 行格式最常用
```

## 4. 分库分表

### 为什么需要？
单表数据量过大（千万/亿级）：索引深查询慢、锁竞争、磁盘备份困难。

### 垂直拆分（按列/业务拆）
- 垂直分库：按业务拆（订单库/用户库/商品库），微服务各管各库
- 垂直分表：大表字段拆多张（常用字段一张、大字段/不常用一张）

### 水平拆分（按行拆）
- 同一张表按规则拆成多张结构相同的表
- 分片规则：分片键取模 / 范围 / 哈希
- 例：`user_id % 4` → user_0~user_3

### 分库分表带来的问题（面试重点）
1. 跨库/跨表查询：join、聚合（count/order by）复杂
2. 分布式事务：多库操作难保证
3. 全局唯一ID：自增冲突 → 雪花算法等
4. 扩容困难：取模后增节点要数据重分布

### 扩容缓解方案
- 一致性哈希：只影响少量节点
- 预分片：先分 1024 虚拟片，映射到少量物理库，扩容只搬映射
- 2 的幂扩容：4→8 翻倍，部分数据位置不变，减少迁移
- 双写过渡：新旧表同时写，校验一致后切换

### 常用中间件
ShardingSphere、MyCat（读写分离 + 分库分表透明化）

## 今日面试考点清单
1. 主从复制三线程？→ dump线程/IO线程/SQL线程；binlog→relay log→重放
2. relay log 作用？→ 存拉取的binlog，供SQL线程重放

6. 扩容难点与缓解？→ 数据重分布；一致性哈希/预分片/翻倍扩容

## 踩坑记录（面试素材）
- 以为所有从库共用一个 dump 线程 → 每从库独立 dump 线程
- 读写分离忘记延迟问题 → 刚写入读不到，强制读主库
- 垂直水平拆分混淆 → 垂直按列业务、水平按行规则
- 取模分片扩容想当然 → 数据重分布是最大难点
- binlog 关闭状态无法复制 → 先开启 log_bin
