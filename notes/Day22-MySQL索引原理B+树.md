# Day22 · MySQL 索引原理 B+ 树（聚簇索引 / 回表 / 覆盖索引 / 联合索引）

> 阶段01 · 第2月 | 配套脚本见 `scripts/day22/` 目录，虚拟机实测通过。
> 背景：索引是 MySQL 性能核心，B+ 树/聚簇索引/回表/最左匹配是面试必考大题。

---

## 1. 索引基础

- 索引 = 书的目录：快速定位数据，减少磁盘 IO
- 本质：**以空间换时间**，索引占用磁盘空间；写操作要维护索引，降低写入性能

## 2. B+ 树（InnoDB 索引底层结构）⭐

B+ 树是 B 树的改良：
1. **非叶子节点只存索引键**，不存数据，只做路由 → 单页能存更多索引，树高更低，IO 更少
2. **所有真实数据都放在叶子节点**
3. **叶子节点双向链表相连** → 范围查询（> < between）找到起点顺着链表遍历

> ✅ 面试一句话：B+树非叶子节点只存索引键、数据全在叶子节点、叶子链表相连，树矮 IO 少、范围查询友好。

**对比 B 树**：B 树非叶子节点也存数据，叶子无链表，范围查询要多次跨节点 IO。
**为什么不用二叉树**：树太深，磁盘 IO 次数多。

## 3. 聚簇索引（InnoDB 核心）

- 数据和主键索引在**同一个 B+ 树叶子节点**（存放整行完整数据）
- 一张表只有 1 个聚簇索引 = 主键索引
- 主键查找：一次 B+ 树检索直接拿到整行

**聚簇索引选择规则**：
1. 定义主键 → 主键就是聚簇索引
2. 无主键 → 选第一个非空唯一索引
3. 都没有 → InnoDB 自动生成隐藏 6 字节 rowid

> MyISAM 不是聚簇索引：数据文件和索引文件分开存储。

## 4. 二级索引（非聚簇索引）& 回表

- 二级索引叶子节点存放：**索引键 + 主键值**（不是整行）
- 查询流程：`where username='xx'`
  1. 二级索引找到叶子节点 → 拿主键 id
  2. 拿 id 回聚簇索引再查一次 → 取完整行
  👉 第二次查询 = **回表**（多一次 B+ 树查找，增加 IO）

## 5. 覆盖索引（避免回表）

- 查询的字段**全部包含在二级索引叶子节点**里，直接返回，不再回表
- explain 的 Extra 列出现 **`Using index`** 即命中覆盖索引

```sql
SELECT * FROM idx_demo WHERE name='zhangsan';        -- 回表，Extra 无标记
SELECT id,name FROM idx_demo WHERE name='zhangsan';  -- 覆盖索引，Using index
```

## 6. 联合索引 & 最左匹配原则

- 多字段联合索引 `(name,age)`：先按 name 排序，name 相同再按 age 排序
- **最左匹配**：从最左字段连续匹配；遇到范围查询（> < between like）停止，后面字段失效

```sql
-- 索引 idx_name_age(name,age)
WHERE name='zhangsan'               -- ✅ 走索引（最左首字段）
WHERE name='zhangsan' AND age=20    -- ✅ 走完整联合索引
WHERE age=20                        -- ❌ 跳过最左 name，全表扫描 ALL
```
> 面试：联合索引优先用最左字段，连续匹配，范围条件后字段失效。

## 今日面试考点清单
1. InnoDB 索引底层结构？→ B+ 树；对比 B 树优势：非叶子只存键/叶子存数据/链表相连/树矮 IO 少
2. 为什么不用二叉树？→ 树深，IO 多
3. 聚簇索引叶子存什么？→ 整行完整数据；一张表一个主键聚簇索引
4. 无主键时聚簇索引？→ 非空唯一索引 → 隐藏 rowid
5. 什么是回表？→ 二级索引拿主键，再查聚簇索引
6. 如何避免回表？→ 覆盖索引（查询字段都在二级索引内）
7. 覆盖索引 explain 标记？→ Using index
8. 最左匹配原则？→ 最左连续匹配，范围条件后失效

## 踩坑记录（面试素材）
- 以为索引越多越好 → 索引占空间、写慢，合理建索引
- 覆盖索引标记记成 Using where → 是 Using index；Using where 是服务层过滤
- 单查 age 期望走 (name,age) 联合索引 → 跳过最左，全表扫描
- 以为 MyISAM 也聚簇 → 数据/索引文件分离，非聚簇
- B 树 B+ 树混用 → 数据位置和链表差异是核心区别
