# Day91 总结笔记：数据服务化

> 日期：2026-11-06 ｜ 模块七：数据平台工程 ｜ 状态：✅ 理论 + FastAPI 实测跑通

## 一、数据服务层解决什么问题

业务直连数仓的 4 个问题 vs 服务层的解法：

| 直连问题 | 表现 | 服务层解法 |
|---|---|---|
| 账号扩散 | 谁都能连库，PII 随便查 | 统一入口 + 权限校验 |
| SQL 口径不一 | 各写各的，GMV 算法不同 | API 内固化 SQL |
| 性能冲击 | 业务高峰打爆库 | 限流 + 缓存 |
| 不可观测 | 谁查了什么不知道 | 审计日志 + 监控 |

价值：**解耦、口径统一、安全可控、性能保护**。

## 二、数据 API 四要素

1. **查询服务**：资源化路径 `/v1/ads/gmv`（版本化）、参数校验（顺序/范围上限）、SQL 参数化、只读账号、超时、统一返回结构
2. **权限三层**：
   - 认证（你是谁）：API Key/Token（系统调用）、JWT（用户级），放 Header + HTTPS
   - 授权（你能访问什么）：RBAC 角色→资源白名单，PII 脱敏/拒绝
   - 审计：记录谁、何时、查了什么
3. **限流**：令牌桶/漏桶、按 Key 配额、并发限制；超限 **429**
4. **缓存**：Redis，key=接口+参数，TTL；三兄弟：穿透/击穿/雪崩

## 三、实操（scripts/day91/gmv_api.py）

- 环境：**独立 venv `~/api_env`**（fastapi + uvicorn + pymysql）
- 接口 `GET /v1/ads/gmv`：API Key 认证 + 日期校验（顺序/≤366 天）+ 参数化查询 `ads_gmv_report`
- 三个测试结果：
  - 带 Key 正常 → 200，4 天数据（3117/6398/59/399）
  - 无 Key → 401 `invalid api key`
  - 范围超限 → 400 `range too large`

## 四、依赖冲突实战（今天最重要的一课）

同一 venv 装 Airflow + 新版 fastapi 出现**双向互斥**：
- Airflow 2.10.3 → `opentelemetry-api==1.27.0`
- fastapi 0.162.0 → `opentelemetry-api>=1.44.0`
- 降 1.27 → fastapi 报 incompatible；升 1.45 → Airflow 的 sdk 1.27 报 incompatible

结论：**调度环境与业务服务环境必须隔离**，各自 requirements.txt 锁版本。

## 五、面试答案

**数据服务层解决什么问题**：业务不直连库，统一入口、口径固化、权限审计、限流缓存，可用可控可观测。
**API 权限怎么做**：认证（API Key/JWT）+ 授权（RBAC + PII 脱敏）+ 审计，三层缺一不可。

## 六、今日小测试（5 题全过）

1. 4 个问题 2. 认证 vs 授权 + 三层 3. 限流 429 / 缓存提性能 4. 只暴露 ADS，直连 DWD/DWS 口径性能失控 5. 依赖互斥必须拆 venv

## 七、易混淆坑

- 认证 ≠ 授权（你是谁 vs 你能干什么）
- API Key 不放 URL，放 Header + HTTPS
- 限流（保护库，429）≠ 缓存（提性能）
- 缓存穿透/击穿/雪崩要能说清
- API 只暴露 ADS 结果层，别直连 ODS/DWD/DWS
