# Day89 实操：订单数仓元数据平台方案（采集→存储→服务）

> 目标：替代 Day64 手工采集（information_schema 手扫 + mermaid 手画血缘 + 数据字典文档），
> 做到技术元数据自动采、血缘自动解析、业务元数据统一登记、对外服务化。

## 一、采集层

| 采集对象 | 来源 | 方式 | 频率 |
|---|---|---|---|
| 技术元数据 | MySQL `dw_project` information_schema（13 表 / 63 字段） | **Pull**（Crawler 增量扫） | 每日 |
| 任务级血缘 | Airflow DAG `etl_order_dw` 的 6 个 task 依赖（task → task） | Pull（读 DAG / 调度 API） | 每日 |
| 表级血缘 | `dws_aggregate.sql`、`ads_report.sql`、各 ETL 脚本中的 `INSERT ... SELECT` | **SQL 解析器**（可接 OpenLineage） | 随代码变更 |
| 业务元数据 | 数据字典（GMV=已支付(status=2)金额、owner、状态枚举） | **Push**（人工表单登记） | 变更时 |

关键点：**任务级血缘（DAG task→task）和表级血缘（表→表）必须两条线都采**——DAG 表达不了表级依赖，SQL 解析才拿得到表血缘。

## 二、存储层（实体-关系-分类）

- **实体**：13 张表 + 63 个字段 + `etl_order_dw` + 6 个 task + 报表
- **关系（Relationship）**：表→表血缘（`ods_order → dwd_order_detail → dws_user_daily/dws_product_daily → ads_gmv_report`）、task→表（`ods_extract` 产出 `ods_order`）
- **分类（Classification）**：
  - 核心表：`ads_gmv_report`
  - **PII**：`biz_user`（手机号/地址/身份证号）、订单收货地址字段、**`dwd_order_detail`（PII 随 ETL 扩散，同样要标）**
  - 临时表/测试表
- **属性**：owner、口径、更新时间、分区

## 三、服务层

1. **搜索**（找数场景）：业务方搜"GMV 口径"直接定位表 + owner
2. **影响分析 / 血缘图**（改数场景）：改 `dwd_order_detail` 前查下游受影响范围（替代 Day64 手画 mermaid）
3. **API**：程序化查血缘，可嵌入发布流程做卡点
4. **权限 + 审计**：谁能看 PII 表、谁改了口径

## 四、平台选型

**DataHub**：有 MySQL / Airflow / dbt 连接器，UI 与搜索现代，支持元数据变更事件流（Kafka）。
备选 Atlas：强绑定 Hive/Spark 生态 + 强合规审计，本场景（MySQL + Airflow）不匹配。

## 五、落地路径（分阶段）

1. **第一阶段**：Crawler 采技术元数据 + 解析 DAG/SQL 建血缘（先把"地图"画出来）
2. **第二阶段**：业务元数据登记（口径/owner），PII 打标
3. **第三阶段**：服务化（搜索/影响分析 API/审计），接入发布流程卡点
