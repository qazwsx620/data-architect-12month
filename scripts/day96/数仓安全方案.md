# 订单数仓安全方案（Day96 实操产出）

> 目标：为订单数仓（ods_order → dwd_order_detail → dws_* → ads_gmv_report）设计一套可落地的安全方案
> 覆盖：分类分级、行级权限、字段级权限/脱敏、加密、审计

## 一、数据资产与分级

| 表 | 主要内容 | 分级 |
|---|---|---|
| ods_order | 原始订单 | 敏感（含 PII，未清洗） |
| dwd_order_detail | 订单明细（order_id/user_id/product_id/amount/status_name/order_date） | 内部 + 敏感（可关联到人） |
| dim_user | 用户维表（user_id/phone/address/id_card/user_name/region） | **机密（PII 集中）** |
| dws_user_daily / dws_product_daily | 主题汇总 | 内部 |
| ads_gmv_report | 报表（stat_date/gmv/order_cnt） | 内部（对外需鉴权） |

分级 → 保护策略：公开/内部可直读；敏感（PII）必须脱敏+权限；机密（id_card）必须加密+最小授权+审计。

## 二、角色清单

ETL 开发、数据分析师（DA）、华东运营、华南运营、财务、外部 BI（合作方）。

## 三、行级权限矩阵

| 角色 | dwd_order_detail | dim_user | ads_gmv_report |
|---|---|---|---|
| ETL 开发 | 全量 | 全量 | 全量 |
| 数据分析师 | 全量 | 全量行（分析需要全区域） | 全量 |
| 华东运营 | `user_id IN (SELECT user_id FROM dim_user WHERE region='华东')` | `region='华东'` | 本区域聚合 |
| 华南运营 | `user_id IN (SELECT user_id FROM dim_user WHERE region='华南')` | `region='华南'` | 本区域聚合 |
| 财务 | 全量（金额/状态逐笔可核） | 全量行，PII 全置空（建议不授此表） | 全量（对账） |
| 外部 BI | 无权 | 无权 | 全量（对外视图 + API Key + 限流） |

实现：
- Hive/Spark：Ranger Row Filter Policy，按用户/组配置上述条件
- MySQL：为每个角色建视图（如 `v_dwd_order_detail_east`），授权到视图而非基表
- API 层：按 token 解析角色，在 SQL 中服务端注入条件，不接受请求参数控制区域

## 四、字段级权限矩阵（dim_user 敏感字段）

| 角色 | phone | address | id_card | user_name |
|---|---|---|---|---|
| ETL 开发 | 全量 | 全量 | 全量 | 全量 |
| 数据分析师 | 掩码 `138****1234` | 城市级泛化 | 置空 NULL | 可看 |
| 华东/华南运营 | 掩码 | 城市级泛化 | 无权（NULL） | 可看 |
| 财务 | 无权（NULL） | 无权（NULL） | 无权（NULL） | 可看 |
| 外部 BI | 无权 | 无权 | 无权 | 无权 |

脱敏策略说明：
- phone：掩码，保留前 3 后 4；运营精确触达走业务系统（OMS/CRM）单次授权 + 留痕
- address：泛化到城市/区县，满足地域分析
- id_card：分析场景用不到，默认置空；对账需要时走加密字段解密 + 单独审批
- user_name：客户名单/回访需要，可全量

## 五、加密决策

| 对象 | 传输 | 存储 | 字段级 |
|---|---|---|---|
| MySQL 连接 | TLS | 磁盘加密 / TDE | — |
| dim_user.id_card | SSL | HDFS Transparent Encryption | 应用层 AES-256 入库（KMS 管密钥，定期轮换） |
| dim_user.phone | SSL | HDFS Transparent Encryption | 应用层 AES-256 入库；另建 phone_hash 列供检索 |
| ods_order 原始数据 | TLS | 磁盘加密 | 同上（原始层 PII 最全，优先加密） |
| 备份文件 | TLS | 磁盘加密 | — |

注意：字段加密后无法 LIKE / 范围查询（索引失效、密文无序）；需要检索/去重时用哈希列。

## 六、审计方案

采集点：
- MySQL：server_audit 插件（记录 user/host/sql/retcode）
- Hive/Spark：Ranger Audit（allow/deny 记录）
- API 网关：请求日志（API Key、接口、参数、返回行数、耗时）
- Airflow：任务操作日志（谁手动触发了哪个 DAG）

日志字段（六要素）：user、timestamp、object（库/表/字段）、action（操作类型 + SQL 摘要）、result（成功/失败/拒绝 + 影响行数）、source（IP/客户端）。

管理：
- 集中落审计库/ELK，append-only（不可篡改），保留 ≥6 个月（生产 1–3 年）
- 告警规则：单次导出 >1万行、非工作时间访问敏感表、敏感表高频访问、deny 次数异常
- 定期报告：敏感表访问 Top、僵尸账号/权限清理、申请权限 vs 实际使用对账

## 七、落地步骤

1. 分级打标：在元数据平台（Day89）给表/字段打敏感度标签
2. 建权限规则：Ranger 策略 / 视图，先覆盖 dim_user 与 dwd_order_detail
3. 脱敏落地：对外视图 + API 层双保险
4. 加密落地：id_card/phone 字段加密 + 哈希列
5. 审计接入：开 server_audit + Ranger Audit + API 日志，配置四条告警
6. 验证：按角色逐个试查，确认越权被拒、脱敏生效、审计留痕

## 八、验收清单

- [ ] 每个角色只能看到矩阵规定的行
- [ ] 敏感字段按矩阵形态返回（掩码/泛化/置空）
- [ ] 越权访问被拒绝且产生 audit deny 记录
- [ ] 密钥在 KMS，代码/配置无明文
- [ ] 审计日志不可被普通账号修改/删除
- [ ] 外部 BI 只能经鉴权 API 拿聚合结果
