# Day98 面试口述稿与薄弱项清单

> 自测日期：2026-11-11 ｜ 范围：调度 / 元数据 / 血缘 / 数据服务
> 评级标准：★★★ 要素齐全 + 结构清晰 + 关键词到位；★★☆ 主干正确但缺关键点；★☆☆ 有明显缺口

## 一、口述稿（已通过部分）

### Q1 为什么选 Airflow（★★★）
> 我们 ETL 是 ODS→DWD→DWS→ADS 四层依赖，要求上游失败下游不执行、失败重试、历史补数，这些都是 DAG 编排能力。技术栈是 Python + SQL，后续要接 Spark/Hive。xxl-job 本质是定时任务中心，表达不了 DAG 依赖；DolphinScheduler 面向 Java 栈、以可视化配置为主，而我们需要代码版本化、可测试。所以选 Airflow。

### Q3 元数据怎么采集（★★★）
> 两条通道：Pull（Crawler 定时扫库）适合技术元数据；Push（Hook/API 上报）适合业务元数据。只有 Pull 会缺业务元数据（口径、owner、主题域）。血缘靠 SQL 解析单独补。

### Q4 Atlas vs DataHub（★★★）
> 深度绑定 Hive/HBase、要求强合规审计 → Atlas；多源异构（MySQL/Spark/云）、要现代 UI 可搜索 → DataHub。

### Q5 血缘两条路线（★★★）
> 解析侧：动态 SQL、变量拼表名、多方言解析不了，只能覆盖有 SQL 的任务；执行侧：侵入引擎、只能采跑过的任务、换引擎要重接。我们实测漏的边全是非 SQL 任务，所以静态解析必须配合非 SQL 任务的显式登记。

## 二、薄弱项（需重点补）

### Q2 任务失败处理（★★☆）— 缺「幂等」
**缺失点**：只说了重试/告警/补数的区别，没说幂等。
**补齐口述**：任务失败先自动重试（`retries` + `retry_delay` 应对抖动），超限告警、人工介入；**重跑和补数都必须幂等**——Hive 用 `INSERT OVERWRITE` 按分区覆盖，MySQL 用 `ON DUPLICATE KEY UPDATE`，绝不能 `INSERT INTO` 追加。
**追问预判**：面试官会问"重跑会不会重复数据？"——答幂等。

### Q6 数据服务四要素（★★☆）— 缺「查询服务设计」
**缺失点**：只答了权限、限流、缓存，漏了第一要素。
**补齐口述**：① 查询服务（版本化路径 `/v1/ads/gmv`、参数校验含范围上限、SQL 参数化防注入、只读账号、查询超时、统一返回 code/data/message）② 权限三层（认证 API Key/JWT、授权 RBAC+PII 脱敏、审计）③ 限流（令牌桶，超限 429）④ 缓存（Redis+TTL，防穿透/击穿/雪崩）。
