# 数仓开发规范（v1.0）

> 覆盖范围：离线数仓（ODW）+ 实时数仓项目 ｜ 维护：数据组 ｜ 生效：2026-11-07
> 定位：团队开发唯一执行标准，进评审与 CI 卡点，不做"挂墙上的文档"。

## 一、命名规范

### 1.1 库 / 表

| 类型 | 规范 | 示例 |
|---|---|---|
| ODS | `ods_{业务域}_{表名}` | `ods_order` |
| DWD | `dwd_{业务域}_{主题}_{粒度}` | `dwd_order_detail` |
| DWS | `dws_{业务域}_{维度}_{周期}` | `dws_user_daily`、`dws_product_daily` |
| ADS | `ads_{报表/主题}_{周期}` | `ads_gmv_report` |
| 实时表 | `rt_` 前缀 或 `_rt` 后缀（与离线物理隔离） | `rt_gmv_1min` |
| 临时表 | `tmp_` 前缀（用完即清） | `tmp_order_clean` |
| 中间表 | `mid_` 前缀 | `mid_user_tag` |
| Kafka topic | `{业务域}_{层}_{主题}` | `ods_order`、`dwd_order_clean` |

规则：表名必须体现**分层 + 业务域 + 周期/粒度**；禁止无前缀的裸表名。

### 1.2 字段

- 全小写 + 下划线；禁止中文、拼音、驼峰、无意义缩写
- 布尔：`is_xxx`（`is_new_user`、`is_refund`）
- 时间：`xxx_time`（`pay_time`、`create_time`）
- 金额：`xxx_amount`（`pay_amount`）
- 数量：`xxx_cnt`（`order_cnt`）
- 标识：`xxx_id`（`order_id`、`user_id`）

### 1.3 分区

- 日期分区统一 **`dt`**，格式 `yyyy-MM-dd`（`dt=2026-11-06`）
- 小时分区统一 **`hour`**，两位补零（`hour=08`）
- 全仓禁止混用 `p_date` / `date_str` / `day`

### 1.4 任务 / 作业

- 命名：`{环境}_{分层}_{表名}`（如 `prod_dwd_order_detail`），**全局唯一**
- Flink 作业名同规则，便于 WebUI 定位与告警归因

## 二、分层规范

### 2.1 职责边界（离线 + 实时）

| 层 | 离线 | 实时 | 允许做 | 禁止做 |
|---|---|---|---|---|
| ODS | `ods_*` 表 | Kafka 原始 topic | 贴源同步、格式统一 | 业务清洗、聚合、删字段 |
| DWD | `dwd_*` 表 | Flink 清洗流 | 清洗、去重、口径统一、维表关联 | 重度聚合（须保持明细粒度） |
| DWS | `dws_*` 表 | Flink 窗口聚合 | 按主题/维度轻汇总，沉淀原子指标 | 做最终报表格式 |
| ADS | `ads_*` 表 | 结果表（JDBC/Redis/CK） | 面向报表/大屏/API 最终汇总 | 回溯加工明细 |

### 2.2 跨层引用规则（红线）

1. 禁止跨层引用：ADS 不直接读 ODS / 原始 topic；DWD 不绕过 ODS 直读业务库
2. 禁止同层互相依赖（DWS 表之间不互读），避免调度成环
3. ADS 只依赖 DWS/DWD，不依赖其他 ADS
4. 实时与离线通过 ADS/DWS 对账，不交叉读对方中间层

## 三、开发规范

### 3.1 SQL 规范

- 禁止 `SELECT *`
- **分区裁剪**：`WHERE dt = '2026-11-06'`，禁止函数包分区字段（`date_format(dt, ...)`）
- JOIN 显式 `ON`，别名统一；大表 JOIN 小表优先广播
- 数据倾斜：加盐 / 两阶段聚合
- 日期参数化 `${dt}`，禁止写死
- 复杂逻辑必须注释口径

### 3.2 离线任务规范

- 一个任务一个输出表，任务名与表名对应
- **必须幂等**：`INSERT OVERWRITE` / 按分区覆盖，重跑不产生重复数据
- 配置齐全：重试次数、超时、告警、上下游依赖
- 禁止读其他任务的中间表

### 3.3 Flink 任务规范（实时）

- **并行度**：按 Source 分区数与吞吐反推；Sink 并行度受连接池约束；禁止默认 1
- **Checkpoint**：核心链路 1 min，一般 3~5 min；最小间隔/超时按间隔取半；快照落 HDFS 保留 2~3 份；语义 `EXACTLY_ONCE`
- **状态后端**：小状态用内存（HashMapStateBackend），大状态用 RocksDB 并开增量 checkpoint + 状态 TTL
- 作业名与环境/分层/表名对应，全局唯一

### 3.4 实时一致性（端到端 Exactly-Once）

- Source：Kafka offset 纳入 Flink 状态，随 checkpoint 快照
- Checkpoint：算子状态与 offset 同一次快照原子写入
- Sink：Kafka 两阶段提交（预提交 → 快照完成 → 提交）；**MySQL 等不支持事务的 Sink 用幂等 upsert 兜底**
- 重跑/重启：从最近成功 checkpoint 恢复 + 幂等保证不重写

### 3.5 脚本与配置

- SQL/脚本版本化入库（Git），不散落服务器
- 连接信息、路径外置配置，不硬编码

### 3.6 数据质量

- 主键唯一、关键字段非空、金额非负、行数波动阈值
- 上线前跑校验，异常告警；实时链路配置双链对账（前提：口径统一）

## 四、评审流程

1. **需求评审**：指标口径、数据来源、粒度确认
2. **设计评审**：分层位置、表结构、分区、血缘影响
3. **代码评审**：SQL 规范、幂等、性能、并行度/checkpoint 配置
4. **上线评审**：质量校验通过、回滚方案、下游通知
5. **上线后**：监控告警 + 对账

## 五、落地手段

- 模板：建表模板、SQL 模板、Flink 任务模板、DAG 模板
- **CI 卡点**：命名检查、SQL 格式检查、禁止 SELECT * 检查
- 元数据平台登记：表/字段/owner/血缘（Day89-90）
- 定期巡检 + 规范评审会；违规问题进复盘
